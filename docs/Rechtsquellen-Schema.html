Rechtsquellen-DB

Schema, Import-Prozess, Zitier-Guard — Kernbaustein gegen KI-Halluzinationen

1. Warum eine eigene Rechtsquellen-DB?

Das Kernproblem

LLMs erfinden Aktenzeichen, Paragraphen und BMF-Schreiben mit hoher Plausibilität. Ein Zitat wie „BFH-Urteil vom 12.03.2023, VI R 42/22" klingt echt, kann aber komplett frei erfunden sein. Wenn solche Referenzen in einem Seminar-Skript stehen und nicht existieren, ist das rechtlich heikel und rufschädigend.

Lösung: Rechtliche Verweise dürfen NICHT frei aus dem KI-Gedächtnis kommen. Sie dürfen NUR aus einer verifizierten Quellendatenbank stammen. Der Zitier-Guard-Prompt zwingt die KI, ohne DB-Treffer stattdessen „Quelle offen" zu schreiben.

3. Import-Prozess

Drei Quellen, drei Importer

  • Gesetze im Internet — gesetze-im-internet.de stellt einen XML-Feed bereit. Importer holt Gesetzestexte, zerlegt sie in Paragraphen, schreibt je Absatz einen Datensatz.
  • BFH-Datenbank — Bundesfinanzhof veröffentlicht Urteile mit Aktenzeichen. Scrape/RSS-Feed liefert Titel, Datum, Volltext.
  • BMF-Schreiben — Bundesfinanzministerium-Newsletter/Archiv mit Verwaltungsvorschriften.

Idempotenz

Der externe_id-Schlüssel setzt sich zusammen als <quelle>:<identifier>:

gesetze-im-internet:arbschg-para3-abs1
bfh:VI-R-42-22
bmf:2024-IV-C-1-S-1234

Mehrfach-Aufruf des Importers erzeugt keine Duplikate. Bei Änderungen der Fassung wird der Datensatz aktualisiert (neue aktualisiert_am-Zeit).

Endpoint

POST /api/v1/rechtsquellen/import
Body: { "quelle": "gesetze-im-internet" | "bfh" | "bmf" }
Response: {
  "neu":           N,   ← Anzahl neuer Datensätze
  "aktualisiert":  N,   ← Anzahl geänderter Datensätze
  "uebersprungen": N,   ← unverändert (Idempotenz-Treffer)
  "fehler":        [ … ]
}

4. Zitier-Guard

Der Zitier-Guard läuft in der Seminar-Generierungs-Pipeline (Sprint 2b). Ablauf:

  1. Die Content-KI erhält ein Seminar-Thema und generiert einen ersten Entwurf.
  2. Vor der Übergabe an die Didaktik-KI: Rechtsquellen-DB wird nach semantisch passenden Chunks abgefragt (pgvector-Nearest-Neighbor).
  3. Die Treffer-IDs werden dem Prompt der Didaktik-KI als „erlaubte Quellen" mitgegeben, zusammen mit strikter Regel:

Zitier-Guard-Prompt-Fragment

Erlaubte Rechtsquellen (mit ID):
  [Liste aus DB-Treffern]

REGEL: Zitiere Aktenzeichen, Paragraphen oder BMF-Schreiben-
Nummern AUSSCHLIESSLICH, wenn die entsprechende ID in obiger
Liste steht. Ohne passenden DB-Treffer schreib stattdessen
„Quelle offen" — auch wenn du meinst, das Aktenzeichen zu
kennen. Frei erfundene Zitate sind untersagt.

So kommen ins Skript nur Zitate, die tatsächlich verifiziert sind. Alles andere wird bewusst als offen markiert und kann von einem Menschen nachrecherchiert werden.

5. API-Endpoints (Sprint 3b)

GET  /api/v1/rechtsquellen?typ=gesetz|urteil|schreiben&q=…&limit=50&offset=0
     → Liste (paginierbar, Filter, Volltext-Suche)

GET  /api/v1/rechtsquellen/{id}
     → Detail mit volltext

POST /api/v1/rechtsquellen/import
     → Trigger für Importer (siehe oben)

6. Update-Prozess

Die Rechtsquellen ändern sich (neue Gesetze, neue Urteile, geänderte Fassungen). Zwei Strategien:

  • Manueller Trigger: Admin ruft POST /api/v1/rechtsquellen/import nach Bedarf.
  • Scheduled Task: Nachts läuft der Importer automatisch für alle drei Quellen (Sprint 3c/3d).

Bei jedem Update-Lauf werden geänderte Datensätze markiert (aktualisiert_am). Themen-Chunks, die auf veraltete Rechtsquellen verweisen, bekommen im Frontend einen Warnbadge („Gesetzeslage geändert seit …") — siehe Etappe 3c.

7. Sicherheits- und Rechtsaspekte

  • Rechtsquellen werden aus offiziellen, öffentlich verfügbaren Quellen importiert. Keine Urheberrechts-Verletzung, aber Quelle immer transparent im UI (Original-Link).
  • Der Zitier-Guard ist kein Ersatz für juristische Endprüfung. Das Seminar-Skript bleibt eine Vorlage, die von einem Fachmenschen freigegeben wird.
  • Bei DSGVO-Anfragen (Betroffenenrechte) sind Rechtsquellen unkritisch — sie enthalten keine personenbezogenen Daten (BFH-Urteile pseudonymisiert).
